## 1. 项目发起人的方向：核心从 Session 转向教师的任务

本次提出的产品方向是：**ClassMatter 应围绕教师要完成的工作组织体验，而不再把 Session / 对话当作产品核心。** 对话仍可用于提出目标、补充信息和讨论，但教师应能持续找到自己正在处理、暂时挂起或等待继续的事情。

- LobeHub 的桌面端体验是本次启发来源之一。
- 「教师有待办、有任务，可以在左侧挂起」是提出的一种直观设想，表达的是任务可持续保留、随时回到工作现场的需要。**左侧位置、列表结构、展示内容与点击后的页面均未确定。**
- 在开发中也参考 Teambition 等任务管理工具，比较它们如何帮助人组织、跟进和完成工作，再讨论适合教师的形态。
- 本次要求是将观点留在 GitHub 供后续参考，不能据此启动一轮未经确认的页面或业务流程重设计。

**明确保留的决策边界：** 整个页面流程、逻辑动线和其他未推进部分，先不作决定。现有已经有较大推进的项目成果应先核对、承接；本记录不授权推翻它们，也不授权把任何新方案直接当成既定流程。

## 2. LobeHub 参考：文章作者的理解，不是已验证的产品事实

公开来源入口：[用户提供的微信文章](https://mp.weixin.qq.com/s/5-D4dNGMuQabYG8izhE5dA)。

**证据限制：** 本次依据讨论中取得的图片转写摘要整理，未独立读取并逐字核对文章原文及原图，也未用官方说明或实际产品逐项验证。摘要中作者将内容标为个人理解、未经官方求证。因此，以下仅列作第三方启发，不声称是 LobeHub 官方承诺、当前已上线能力或确定的技术实现。

摘要中可供后续核验的主题包括：

1. 从会话转向任务，任务描述可以修改。
2. 执行过程中产生验收清单并进行自检。
3. 多 Agent 分工、通过 @ 指向协作者。
4. 探索依据消息上下文主动协作，以及用规则筛选是否介入。
5. Router / Worker 的分工思路。

这些主题值得研究的是：目标怎样被保留和修订，工作怎样继续，结果怎样被验证，主动协作何时真的有用。它们**不等于** ClassMatter 已选用多 Agent、@ 交互、Router / Worker 架构或自动执行模式；选型与实现仍须有独立证据和批准。

## 3. Teambition 对照：研究任务管理，不照搬产品界面

项目发起人提出将 Teambition 等工具作为另一类参考。本次未做功能盘点或实测，以下为 **AI 整理的待研究维度**，不表示这些具体能力已在某个版本中得到验证：

| 对照维度 | 后续要回答的问题 |
|---|---|
| 任务与对话的关系 | 教师能否不翻找聊天记录，就理解一件工作的目标、进展和下一步？ |
| 挂起与继续 | 等待材料、等待教师判断或暂时中断后，恢复工作需要重新交代多少信息？ |
| 子任务与依赖 | 哪些教师工作值得拆分，哪些拆分反而增加管理负担？ |
| 进展与完成 | 怎样区分执行过、产物已生成、已检查和教师接受结果？ |
| 资料与产物 | 任务如何关联必要来源、可编辑草稿和最终结果，避免材料散落？ |
| 协作与提醒 | 谁需要行动、为什么需要、何时提醒，怎样减少无效打扰？ |

LobeHub 讨论提供的是 AI 协作启发，任务管理工具提供的是工作组织对照。二者都只是参考，不能凭类比决定教师场景的对象模型、权限、任务状态或界面布局。

## 4. AI 整理建议：将目标、执行与验收分开讨论

以下是为后续讨论提出的建议，**不是项目发起人已经确认的需求**：

- **任务应能跨对话继续。** 可以研究让任务关联目标、必要上下文、产物和未完成原因；Session 只是某次协作的入口。是否需要新增对象，应先检查现有 Task 与持续会话能力，而非另起一套平行系统。
- **目标改变时，旧计划与验收也要重新看。** 任务描述可修改这一启发，值得转化为对版本、范围变化和过期结果的研究问题，不能静默扩大授权。
- **自检不是最终验收。** AI 生成的清单可以帮助检查遗漏，但不能自行降低教师要求，或以自报成功代替可核验的产物和证据。哪些条件能由确定性检查验证、哪些须由教师判断，仍待讨论。
- **主动协作要有边界。** 可研究在已授权来源中发现缺项、提出下一步或准备草稿；是否自动推进、怎样分工和何时打扰教师，应逐类任务明确。多 Agent 不能增加权限，收到消息也不等于接受任务或取得执行授权。
- **以净减负衡量形态。** 后续可比较任务中心和会话中心在恢复工作、寻找资料、核对结果上的总耗时，以及重复交代、错误关闭和无效提醒。不能只以任务数量或 Agent 数量衡量进步。

只用虚构的备课、班会材料整理等一般性任务讨论这些问题；具体案例、指标和实验是否开展，也应另行确认。

## 5. 与现有项目的关系及保持不变的边界

现有产品已经强调以事为中心，并有 Record / Task / Today / Timeline 的工程基础；既有研究也讨论了 Work Item 跨 Session 保留、完成证据和主动推进。本次记录是对产品组织重心与参考对象的补充，不能把已有实现说成尚未开始，也不能把既有研究候选说成已实现。

- 不修改现有页面、导航、持久化会话或已推进的工作流。
- 不修改 R1 manifest、canonical requirements、API、数据库、Eval / Task / Gate、权限或发布状态。
- 保留 Query Gateway / Business Command Gateway / Identity Security Boundary；AI 只读与草稿的现行边界不变，正式写入和外发需要相应授权。
- 不引入真实学生数据、私人消息全文、身份映射或未经授权的外部服务传输。

后续若形成实施提案，应先核对当前代码和已经推进的成果，再由项目发起人确认范围，通过现有需求、架构、评测与发布治理流程推进。

## 6. 留待讨论的问题

1. 哪几类教师工作最需要跨时间保留和恢复？哪些短问答仍保留为普通对话即可？
2. 教师口中的「任务」对应现有 Task、一个更长的工作专题，还是多个已有对象的组合？先验证语义，不先建表。
3. 对话、任务、来源和产物怎样关联，才能减少寻找成本？具体页面和跳转动线暂不确定。
4. 左侧挂起只是一个候选例子。是否采用、与已有导航怎样兼容，需要哪些实际使用证据？
5. 验收条件由谁提出和确认？目标变化后怎样处理过期清单、自检结果与教师已接受的产物？
6. 哪些主动行为仅产生建议或草稿，哪些可能需要明确授权？单 Agent 是否已足够，何时才值得增加分工？
7. 从 Teambition 等工具借鉴什么会真正减负，哪些项目管理概念对教师反而过重？

**当前结论止于方向与问题清单：以教师任务为中心，结合 AI 协作与任务管理工具继续研究；不在本记录中确定具体软件形态或实施路线。**

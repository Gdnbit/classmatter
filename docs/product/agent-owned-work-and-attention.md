# Agent 承接可执行工作：从教师 Todo 到可信的班务持续推进（研究提案）

> 状态：**Discovery / Future · 非 R1 规格 · 未实施 · 未验证用户价值**
>
> 研究日期：2026-10-22；适用产品：班事有谱 · ClassMatter（Agent-native Personal Class OS）。
>
> 本文记录一段关于「AI 应有自己的待办，持续检查并自行完成可执行事项；只向人请求必要参与」的视频带来的设计启发，以及进一步的业务抽象。视频属于**启发材料**，不是已经验证的用户需求、法律依据或产品效果证据。为保护原始信息，不转载聊天原文、学员信息、客户信息或未经授权的素材。

## 0. 研究结论（不是发布承诺）

**班主任掌握职业判断与组织责任；ClassMatter 掌握业务事实、持续事项状态、可追溯记忆与调度；Agent 仅作为可替换、按需运行的执行能力。**

- 原来的价值：让班主任不靠个人记忆维持全部未闭环事项，在适当时间重新浮现。
- 下一步候选价值：在适当授权、规则和证据下，由系统**主动推进可自动处理的环节**，只把判断、批准、缺失信息和线下行动交给教师。
- 重要边界：「Agent 的任务」只是**执行委派**，不是法律、学校或组织意义上的责任转移；“已发送”也不是“对方已接收或正式接手”。
- 实施边界：不修改 R1 manifest、107 项规格需求、Eval / Task / Gate、数据库、API/Tool、当前风险等级或真实数据准入条件。本文不会把自动化、主动提醒、敏感学生数据处理变成已交付能力。

## 1. 从视频提炼出的问题

典型模式：一条外部业务消息被沉淀到知识库后，系统识别出待办并提醒人去处理；但如果某一步已有安全、授权的自动化能力，就不应继续要求人执行这一步。真正的人类待办应是「需要人提供信息／判断／批准的局部动作」，其余由系统在条件满足后继续推进。

它提示了三个问题：

1. **谁应该执行下一步？** 人、Agent、既有业务系统还是外部协作方？
2. **为什么当前不能继续？** 缺信息、缺权限、等待时间、外部反馈、风险审核还是业务终止？
3. **谁判断事情真的结束？** 不能仅凭 Agent 的自然语言“完成了”；需要可核验的业务完成条件和证据。

这比「给 AI 加个 Reminder」更底层：Reminder、日历、任务面板只是投影；真正需要的是有生命周期的工作事项。

## 2. 与 ClassMatter 现有定位的关系

ClassMatter 已定位为 **External Working Memory + Closure Engine**（外置工作记忆 + 事务闭环引擎），当前 R1 的最小链条是 Record → Task → Today / Student Timeline，Agent 仅查询与草稿。

未来方向可以从「系统准确记住并重新浮现」扩展到「系统在权限允许时主动推进」，但不能损害既有原则：

- 首要价值仍是降低遗漏、交接断裂和不清楚的责任压力，**不是自动化越多越好**；
- 对事实、观察、推断、草稿、知识与会话记忆保持权威边界；
- 组织责任、授权与被委派执行相互独立；不把收到一条消息等同于接受派责；
- AI 不可用时，UI/正式业务流程仍然能完整使用；
- 更少打扰不等于隐藏风险；安全、及时处置与可追溯优先于降低提醒数量。

## 3. 最小的业务语义分解（提案）

下表是**概念职责**而非要求立刻新增表：

| 概念 | 表示什么 | 不应与什么混为一谈 |
|---|---|---|
| Event / Record | 已确认发生了什么、谁记录的、证据与更正版本 | Agent 推断 |
| Case / Open Loop | 哪件事还没有结束、为什么尚未结束 | 单个 Todo 或 Agent Session |
| Task / Work Item | 下一步可执行动作、预期结果、执行者候选 | 正式责任分配 |
| Responsibility / Authority | 依据规则和组织关系确认的责任与授权 | Agent 接到了一个任务 |
| Trigger / Schedule | 何时、在何种可验证条件下重新评估 | Calendar 提醒本身 |
| Execution Attempt | 具体一次执行、输入版本、工具回执、错误与耗时 | “业务已经完成” |
| Completion Evidence | 满足何种可验证标准才算关闭 | 模型自报成功 |
| Attention Projection | 现在要人关注什么、原因、急迫性、可采取动作 | 第二套事实数据库 |

优先使用已存在的 Record / Task / Today / Timeline 以及领域规则来验证是否足够；**禁止直接建一张无约束的万能 Open Loop/Memory/Fact 表**。必要的新领域对象需经过未来 release 的 SDD / ADR、迁移、API、Eval 和数据治理审批。

### 工作生命周期候选

~~~text
Capture / 已有业务事件（先确认来源与身份）
    → Draft / Candidate（尚未升级为正式事实）
    → Validated Work Item（经授权规则登记）
    → Ready
       ├─ 人类所需 → Needs Human（判断／补信息／批准／线下行动）
       ├─ 条件不满足 → Waiting（事件／时间／第三方）
       └─ 可自动执行 → Running（工具白名单、幂等、租约）
    → Verifying（校验业务结果与证据）
       ├─ Done / Closed（已满足定义的关闭条件）
       ├─ Waiting / Review（证据不足）
       ├─ Failed / Escalated（超限、异常、人工兜底）
       └─ Cancelled / Superseded（取消、来源更正或版本取代）
~~~

并非每个事项都有截止日期；例如“观察中”“等待确认收到”“需复访”可能只有重新评估条件。状态改变须记录原因、主体、版本和必要的审计证据；改变正式业务状态必须遵守 BCG，不能因为 Agent 推断为 Done 就直接关闭。

## 4. ClassMatter、记忆系统与 Agent 的所有权

**ClassMatter 自己管理以下事实和系统机制：**

1. **业务状态**：类型化记录、Case / Task / Work Item、责任和执行授权、生命周期与完成证据。
2. **记忆与上下文**：业务事实、规则版本、Knowledge/Wiki、可撤销偏好、检索索引、对话/运行摘要的用途与保留期。
3. **调度与恢复**：可靠触发、条件检查、Outbox、超时/重试、取消、升级、停机恢复。
4. **治理与展示**：身份/目的/租户隔离、QG、BCG、ISB、审计以及教师看到的 Today/AI Inbox。

**Agent Runtime（当前为 Pydantic AI，未来可以比较 Pi）只负责：** 被唤醒时理解 ClassMatter 允许提供的上下文、制定本次局部计划、调用允许的工具、返回结构化候选/结果。模型会话、压缩摘要、工具轨迹可以帮助执行，但**不是正式业务事实、批准或持久化业务事项**。

因此：

- Session 可以结束、压缩、失效、换模型、替换框架；Work Item 不得丢失。
- Memory 与 Knowledge/RAG 不等于 Domain Fact；检索所得文本不能直接授权写入或越权操作。
- 更正、删除或授权撤销后，应能识别相关来源版本，令其派生摘要、索引、任务候选和触发失效/重审。
- 持久会话/压缩不是 Durable Business Workflow。运行时即使有 durable execution，正式业务状态仍由 ClassMatter 持有。

## 5. 两个可验证的**虚构**班务案例

### A. 请假未归的核对（优先验证，低敏模拟）

- **输入**：合成学生的请假事实、结束时间、教师确认的跟进要求。
- **系统可做**：在约定时间查询现有销假记录；没有结果时形成需老师核对的候选；有来源可验证的销假信息时建议完成该跟进。
- **需要人**：联系学生或家长、决定是否升级处置，以及现阶段适用的关闭批准。
- **不能做**：仅凭聊天摘要推断学生安全、自动标记真实销假、未经授权外发消息。

### B. 已沟通但等待回执（等待条件案例）

- **输入**：老师在可信 UI 记录“已通知，等待确认收到”。
- **系统可做**：保留发送与接收**不同**状态；在合法渠道有可靠回执时重新评估；逾时提醒教师判断是否另行沟通。
- **需要人**：决定是否再次发送、是否完成责任交接。
- **不能做**：把“消息已发”当作“对方已确认”或“责任已正式转移”。

高风险学生心理、健康、家庭与紧急事件属于独立治理范围。**现实紧急事件优先按学校正式流程立即线下处置，不能等待 Agent、AI Inbox 或定时任务。**

## 6. Today：从教师 Todo 到人机协作的 Attention

未来 Today 可以研究对同一可信事项状态的**不同投影**：

- **需要我处理**：只显示必须由老师判断、批准、补信息或采取线下行动的环节；
- **系统处理中**：已授权的低风险工作及其当前步骤、下一次检查点；
- **等待中**：等待回复、条件、外部系统，且可说明何时重新浮现；
- **异常或需升级**：重试失败、来源冲突、逾时、安全风险、责任交接缺失；
- **最近已闭环**：关闭的证据、版本、来源与可追溯记录。

这不是新的事实源，且不能为了“少提醒”压低必须及时看到的安全事项。AI 自行安排 Work Item 也不代表自己获得组织身份或正式责任。

## 7. 企业流程与 ClassMatter 的抽象边界

同一模型可用于企业里的文件核验、补件、审批等待、业务回执等，但本仓库**仅讨论通用原则，不披露任何非公开企业客户、合同、联系人、业务数据或内部系统实现**。

可跨领域复用的是 Context Policy、Work Runtime 抽象、触发/恢复、可观测性和受控 Tool Port；班级领域的事实、权限、敏感度、学校规则与风险分类必须留在 ClassMatter 的 Domain Pack。暂不建立独立“万能企业 AI 平台”。

## 8. 可靠执行：运行时不能替代领域信任边界

建议未来实验优先验证：

- 事件触发优先于无边界轮询；有期限、幂等键、最大重试、指数退避和人工兜底；
- Worker 崩溃、调度重复投递、网络重试与回执丢失时，仍不重复提交同一正式写操作；
- 工具调用前**重新校验**身份、目的、权限、scope、来源版本和资源状态；不能只相信开始时的计划；
- 最小权限白名单，默认没有 Shell、任意文件系统、SQL、外网浏览或任意 MCP 工具；
- 每次执行独立记录 tool name/version、输入摘要/事实版本、结果回执、异常、审计关联，且隐私最小化；
- 人类确认事项有独立的失效、拒绝、超时路径；失效批准不能被重放；
- 触发默认生成 Candidate / Review Item；任何正式写入需经过既有 QG/BCG/ISB 与未来 Release 明确授权。

## 9. 假设、风险和真实价值验证

这仍是**研究假设**，不是班主任真实痛点已经得到证明。最关键的验证目标不是“Agent 做了多少任务”，而是：

- **每个完整业务闭环的人类主动介入次数**是否下降；
- 教师的净耗时（录入 + 审核 + 纠错 + 提醒打断 + 维护）是否下降；
- 未处理/错误对象/误关闭/错误转交/迟到的风险是否不劣于原流程；
- Agent-off、服务重启、来源更正、审批超时后是否能正确继续或停止；
- 是否提高了老师“可以放心交给系统”的主观信任，但不要求盲目信任。

必须先在**纯虚构、合成数据**中验证，然后通过独立产品、隐私、安全、运维与用户研究 Gate 才能考虑真实试点。

## 10. 开放问题与后续材料

1. 是否真的存在高频、可验证、低风险而值得自动推进的班务动作？
2. 现有 Task + Timeline 是否足以表达等待/重开，何时才有证据支持 Case/Workflow 独立领域对象？
3. 何种完成标准能由确定性规则校验，何种必须由教师确认？
4. 如何为长周期任务设置合理的醒来条件，而不制造轮询成本和提醒噪声？
5. 哪些记忆必须独立保留，哪些应仅在临时 Session 中存在？
6. 在风险、费用、依赖和可维护性都可接受时，是否仍有替换 Agent Runtime 的明确收益？
